# تحليل المشروع قبل وبعد التصحيح

## الحالة الأصلية

كانت النسخة الأصلية PWA كبيرة مبنية بـ HTML وCSS وJavaScript دون build step. احتوت على الدراسة والاختبار والملاحظات والمفردات وتسجيل البريد عبر Supabase، لكنها كانت تخالف المتطلبات الأساسية في نقاط جوهرية:

- التنزيل والتخزين على مستوى السنة كاملة في `year_data_*`.
- زر التحديث اليدوي يكتشف ملف مادة جديداً فقط، ولا يكتشف سؤالاً جديداً داخل ملف قائم.
- عملية يومية كانت تنزّل ملفات المواد المتغيرة والجديدة تلقائياً وتحذف الملفات التي اختفت من المصدر.
- المزامنة السحابية كانت تشمل الكلمات والملاحظات فقط، ولا تشمل `progress_*` أو `app_last_position`.
- بيانات جهاز واحد لم تكن معزولة حسب الحساب، ما قد يخلط بيانات حسابين متتاليين.
- الحذف أثناء عدم الاتصال لم يكن يسجل tombstone فورياً.
- صف JSON السحابي كان يُكتب بأسلوب read/merge/upsert دون مقارنة مشروطة، ما يسمح بفقد تحديث متزامن.
- ملف `content-manifest.json` كان قديماً: احتوى ثلاثة مسارات غير موجودة وأسقط مادة موجودة، مع hashes قديمة لعدة ملفات.
- معظم الأسئلة لم تكن تملك معرفاً صريحاً، وبعض المعرفات الموجودة كانت مكررة.
- `feedback` ونص تحليل النطق كانا يُحقنان في HTML مباشرة.
- الواجهة المخفية القديمة كانت تطلب GitHub PAT وتخزنه في localStorage.

## التصميم الجديد

### 1. المحتوى والأوفلاين

- `subject-storage.js`: مستودع IndexedDB ذري، سجل واحد لكل مادة، مع ترحيل تلقائي من تخزين السنة القديم وبديل localStorage.
- `content-catalog.js`: قراءة فهرس v2 صغير وتخزين آخر نسخة منه، وحساب الحالات `download/current/update`.
- `app-v12.js`: واجهة كتالوج مستقلة لكل مادة، تنزيل/تحديث المادة المطلوبة فقط، والتحقق من SHA-256 والمخطط قبل commit.
- `service-worker.js`: App shell إصدار 13، قاموس محلي ضمن الكاش، ولا يقوم أبداً بتحميل ملفات المواد في الخلفية.

### 2. قواعد الأزرار

| حالة المادة | الزر الظاهر |
|---|---|
| غير محمّلة | تحميل |
| محمّلة وhash مطابق | فتح + إزالة، بلا تحديث |
| محمّلة وhash مختلف | فتح + تحديث + إزالة |
| مادة جديدة غير محمّلة | تحميل فقط |
| دون إنترنت وغير محمّلة | تحميل معطل |
| دون إنترنت ومحمّلة وقديمة | فتح + تحديث معطل + إزالة |

### 3. مزامنة الحساب

الحمولة v2 تشمل:

- المفردات مع `updatedAt`.
- الملاحظات مع timestamp لكل مفتاح.
- تقدم الدراسة والاختبار في جميع مفاتيح `progress_*`.
- آخر موضع في `app_last_position`.
- tombstones للمفردات والملاحظات والتقدم.

تستخدم الكتابة `updated_at` كقيمة مقارنة متفائلة؛ عند تعارض جهاز آخر يعيد التطبيق القراءة والدمج والمحاولة. يحتفظ التطبيق أيضاً snapshot محلياً لكل `userId` كي لا يرفع بيانات حساب A إلى حساب B.

يملك كل جواب `updatedAt` مستقلاً، لذلك يمكن دمج جواب سؤال من جهاز مع جواب سؤال آخر من جهاز ثانٍ. كما تستخدم دورة المزامنة عداد تغييرات وحقبة للحساب؛ إذا عدّل الطالب بياناته أو بدّل الحساب أثناء انتظار الشبكة، تُلغى نتيجة الدورة القديمة وتُعاد المحاولة بدلاً من الكتابة فوق البيانات الجديدة.

### 4. سلامة البيانات والأمن

- أُزيلت واجهة GitHub PAT القديمة.
- عُرض feedback ونصوص المصادر باستخدام text nodes أو escaping.
- تسجيل الخروج أصبح محلياً لهذا الجهاز (`scope: local`).
- SQL يضيف RLS وقيود JSON/الحجم وtimestamp خادمياً.
- كل سؤال يملك الآن معرفاً ثابتاً وفريداً مكتوباً في JSON.
- أضيفت معرّفات توافق ذات أولوية للإصدار القديم؛ وبذلك لا تسرق الأسئلة المتشابهة معرّفات بعضها عند ترحيل التقدم والملاحظات.
- manifest v2 مشتق آلياً من الملفات الحقيقية ويشمل الاسم واللغة وعدد الأسئلة والحجم وSHA-256.

## نتائج فحص المحتوى

- 20 ملف مادة صالحاً.
- بدأ التدقيق من 4068 سجل سؤال تاريخي.
- دُمجت 765 نسخة مكررة ضمن 539 مجموعة مراجَعة، وحُذفت 10 أسئلة ملتبسة أو غير قابلة للإجابة، فأصبح البنك 3293 سؤالاً فريداً.
- طُبقت 86 عملية تصحيح أو إعادة صياغة صريحة على مفاتيح الإجابة، والخيارات، والأسئلة الناقصة أو الملتبسة.
- نتيجة التدقيق النهائي: صفر نصوص سؤال مكررة، صفر مجموعات صارمة مكررة، صفر تعارضات متطابقة، صفر خيارات مكررة، وصفر فهارس إجابة غير صالحة.
- بقي زوجان متشابهان عن قصد: إسناد Aristotle/Coleridge المتعاكس، وسؤال Beckett الإيجابي مقابل سؤال `NOT`. لا يمثلان تكراراً دلالياً.
- جميع معرّفات السجلات المدمجة أصبحت aliases للسؤال الباقي؛ أثبت اختبار الانتقال تحويل 4068 سؤالاً تاريخياً إلى 3293 سؤالاً حالياً + 765 مدمجاً + 10 متقاعدة دون فقد مسار التقدم.
- صُححت لغة `Third Year/french.json` إلى `fr` ولغة `Fourth Year/Modern_Drama.json` إلى `en`.

## حدود واضحة

- الإشعار عن المحتوى هو إشعار داخل التطبيق عند الفتح أو عودة الاتصال أو الفحص الدوري المدعوم. إشعار Push أثناء إغلاق التطبيق كلياً يحتاج خادماً يرسل Web Push، وهو خارج ملفات موقع ثابت فقط.
- العمل دون إنترنت يبدأ بعد زيارة HTTPS ناجحة وتنزيل المادة المطلوبة.
- Supabase يجب أن يكون معداً فعلياً باستخدام ملف SQL؛ لا يمكن للملف المضغوط تنفيذ إعداد قاعدة بيانات خارجية وحده.
- سرعة النطق والتحليل الخارجي يعتمدان على خدمات المتصفح/الإنترنت، أما الأسئلة والملاحظات والتقدم فتعمل دون إنترنت.
